# ADR-0008: Reviewed continuation of independent authorized laboratory work

Status: authorized by the owner on 2026-11-16 under AB#301.

## Problem

The reviewer can approve stopping an inconclusive diagnostic and moving to another
already authorized journey, but the dispatcher only understands material product
progress or technical correction. At the global preparation bound it discards that
handoff and reports a Codex failure. The owner becomes a relay even though there is
no missing product decision or credential. Pass235 is a concrete instance: the WTS
inventory completed cleanly and review selected independent Web ZIP work.

## Decision

Add a typed optional `workContinuation` selection to independent review. Prose,
model-produced work items, a changed title or source filename never grant it. The
versioned eligible targets are `web-entries`, `managed-technical` and
`negative-consent-cleanup`, already present in the current Task contract. This
continuation never grants IDE/model inference, Linux retries, acceptance, new
resources, credential changes or an increase to experiment deadlines or quotas.

The first selection must be an independently approved, clean offline handoff to a
different eligible objective. The host derives its identity and budget from the
immutable protected checkpoint chain, not a model count or an editable file. Each
target can be entered at most once for this preserved campaign. There are at most
two offline preparation checkpoints and one independently approved runtime
checkpoint per target. Each checkpoint permits exactly one executor launch,
including interrupted launches. Runtime retains the existing read_only_preflight
or bounded_no_model safety/evidence/cleanup validation. The reviewer must bind the
actual prepared source and describe the exact permitted next action; a handoff is
not a free-form execution grant or permission to skip consent.

Every use is persisted before resuming the executor. Replay reuses the same grant;
source/name churn cannot refund it. Technical corrections keep their existing
independent limits and cannot reset the consumed work-continuation history.
Historical preparation counts remain unchanged; neither switching objectives nor
finishing a diagnostic counts as product evidence. Verified new material evidence
continues through the existing evidence rules. A target with no grant remaining
stops visibly or the reviewer may select another eligible unvisited target;
it cannot bounce between already used targets.

The controller and user-facing status distinguish pending independent work from
an exhausted technical correction or a transport error. Routine approved handoffs
are delivered by the existing timer without an operator checkpoint. Existing
stalled historical results remain immutable: installation may re-review an exact
saved snapshot under the new typed contract in a separate protected job. It cannot
parse old nextAction prose as authority, overwrite its result, reset counters, or
open a new inference allowance. Only independently reviewed typed output activates
the bounded handoff and releases the matching operational gate.

## Review context and corrected-source resumption

A tool-less work review receives the exact hash-bound original verdict and its
reviewed objective as data. The proposed next target is separate; classifying the
past evidence as the proposed target is invalid. An exhausted diagnostic branch
cannot obtain another probe through a null work selection. A fresh valid
typed selection authorizes a new target or runtime checkpoint. The same-target
offline correction below uses the existing grant and typed independent rejection.

If a work review stalls because its installed source requires correction, a new
job is allowed only after the bound source files change, with the original
campaign, executor result and candidate intact. The complete previous job is
retained by a protected hash inventory. Its consumed review attempts are carried
forward before the new marker is exposed. A work re-review has a total ceiling of
three model calls across these jobs, independent of generic recovery windows.
Source changes, retries and new job names cannot renew that ceiling. An exhausted
review remains stopped; no old verdict is rewritten or promoted to authority.

## Same-target offline correction

An independent `changes_requested` review already requests correction of its
identified defects. Repeating the selected target in a nullable selection field
must not prevent that existing work from returning to its executor. The host may
derive exactly one same-target offline correction when the immediately active
protected grant is offline with one preparation and zero runtime checkpoints,
the reviewed pass equals that grant's next pass, and the validated review names
the same objective, has nonempty findings, offline scope, clean cleanup and no
owner request. Its source and evidence remain bound to the exact candidate.

The host never reads nextAction prose to choose this route. A null selection still
grants no new target or runtime. The derived checkpoint records
`workContinuationDerivation=same_target_offline_correction`, consumes preparation
slot two, and permits one executor launch. Further rejection cannot create a third
preparation or fall back to a technical route to evade that limit.

For an already stalled exact rejection, the host archives the stopped marker and
matching operational retry, replays the reviewed result without rewriting it or
adding objective history, persists the new checkpoint, and only then releases
that exact gate. Findings, preparation counters, inference ledgers and prior
review-call consumption remain unchanged. This recovery requires no new model
review and does not promote the rejected candidate to runtime or acceptance.

## Verification

Regressions must cross the real review/finish/checkpoint boundary: the previously
stalled approved handoff continues with typed authority, and unchanged counters,
authorization, history and ledger. Reject prose-only selection, same/unknown or
unapproved target, unresolved cleanup, missing/mismatched source/evidence, owner
requirement, repeated target, third preparation and second runtime. Exercise
interrupted launches, checkpoint replay, stale snapshots and exact current-stall
adoption. Failed checks never authorize runtime or entry into another target. A requested
offline correction of the active target consumes its remaining preparation slot;
it does not refund a grant. Real rollout verifies a new
executor pass; it does not claim that its product journey has passed.

## Fixed host execution of the reviewed Web ZIP journey

The owner-authorized assisted repair of the rejected pass237 packet is installed
as a fixed Web ZIP entrypoint. The existing campaign wrapper dispatches this
specific operation on the host, using a protected `webZipRequest` and the existing
`web-entries` runtime grant. It does not run a model to execute protected files,
introduce another service/counter, restore an offline allowance, or change the
inference ledger. `begin` and `finish` remain the existing controller operations.

The request binds the immutable predecessor as `previousReview`. The new
correction binds the request hash; the new review binds the correction; the
campaign selects that current review. This acyclic order preserves exact current
authority, candidate, pass, installed source hashes and desktop/product inputs.
The host validates the complete grant history before one launch. Source or request
changes require fresh review; an offline test verdict is not a runtime grant.

A host intent is published atomically and durably before invoking the installed
Node entrypoint. Interrupted intent, partial output and partial entrypoint intent
produce unresolved evidence without another guest launch. Reconciliation runs
before the normal phase gate, including when that gate has already moved a
consumed launch to review_pending. It neither restores active state nor decrements
counters. Protected host result and packet references bind the ordinary independent
review to exact output bytes. Only a completed, settled run supplies current-pass
runtime evidence; that evidence never changes documented acceptance by itself.

The owner separately authorized completing ordinary official Web login inside the
same owned Edge instance/profile. The fixed existing private LAB credential file
is read as data only, never sourced as shell code or copied into the request or
review package. SSH stdin carries runtime-only login material; DPAPI CurrentUser
protects its temporary Windows file. The official login form is submitted once,
with network recording disabled during authentication, inside the unchanged
600-second absolute operation budget. The parent verifies temporary login-file
removal independently of primary evidence writes. No copied cookies, registration,
password reset, OAuth reauthorization, credential rotation or new account is
permitted. A failed login is unresolved, not inferred owner action or acceptance.

Local Node/PowerShell process regressions use synthetic credentials and explicit
Windows/DPAPI/UI doubles. Their passing result does not establish native Windows,
PowerShell5.1, DPAPI transfer, an authenticated desktop, upload or scanner success.
Actual observed SID/session and the existing authorized product are required
before the protected runtime request can be admitted. The first-upload correction
below replaces the initial requirement for a pre-existing ZIP definition/revision. Original
review237, earlier packets, all preparation counts and the inference ledger remain
immutable. See `ops/joao/web-zip/README.md` and the host rollout procedure.


## First-upload input correction

The bounded official catalogue observation found one accessible product with eleven
active LocalFolder/SelfHosted definitions and no UploadedZip/Managed definition.
The first-upload Web journey already creates the definition and execution in one
confirmed upload; requiring a pre-existing ZIP definition was a runner prerequisite
error, not a product requirement or a reason to ask the owner to fabricate IDs.

The same fixed entrypoint now binds an existing product, a restricted synthetic
analysis name and `Development`. It follows the published v0.92.0 creation wizard,
observes one `createUploaded` request, and obtains the definition and revision only
from its response. Request metadata, returned product, rendered execution, exact
revision, definition and history must agree. The host packet checks these bindings.
No product creation, preparatory scan, separate configuration or old rerun branch
is introduced. Full rendered coverage excludes partial Semgrep coverage even when
all three tool processes completed.

This source correction does not change the protected grant, launch allowance,
600-second deadline, counters, historical evidence or installation. The existing
reviewed host authority still controls runtime. Offline browser primitives and
Windows process doubles do not establish native picker, DPAPI, login or live scan
success; the real journey remains outstanding until its bound evidence is reviewed.
