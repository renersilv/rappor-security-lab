# ADR-0008: Reviewed continuation of independent authorized laboratory work

Status: authorized by the owner on 2026-11-16 under AB#301.

## Problem

The reviewer can approve stopping an inconclusive diagnostic and moving to another
already authorized journey, but the dispatcher only understands material product
progress or technical correction. At the global preparation bound it discards that
handoff and reports a Codex failure. The owner becomes a relay even though there is
no missing product decision or credential. Pass235 is a concrete instance: the WTS
inventory completed cleanly and review selected independent Web ZIP work.

## Decision

Add a typed optional `workContinuation` selection to independent review. Prose,
model-produced work items, a changed title or source filename never grant it. The
versioned eligible targets are `web-entries`, `managed-technical` and
`negative-consent-cleanup`, already present in the current Task contract. This
continuation never grants IDE/model inference, Linux retries, acceptance, new
resources, credential changes or an increase to experiment deadlines or quotas.

The first selection must be an independently approved, clean offline handoff to a
different eligible objective. The host derives its identity and budget from the
immutable protected checkpoint chain, not a model count or an editable file. Each
target can be entered at most once for this preserved campaign. There are at most
two offline preparation checkpoints and one independently approved runtime
checkpoint per target, except for the explicitly authorized Web ZIP retry amendment
below. Each checkpoint permits exactly one executor launch,
including interrupted launches. Runtime retains the existing read_only_preflight
or bounded_no_model safety/evidence/cleanup validation. The reviewer must bind the
actual prepared source and describe the exact permitted next action; a handoff is
not a free-form execution grant or permission to skip consent.

Every use is persisted before resuming the executor. Replay reuses the same grant;
source/name churn cannot refund it. Technical corrections keep their existing
independent limits and cannot reset the consumed work-continuation history.
Historical preparation counts remain unchanged; neither switching objectives nor
finishing a diagnostic counts as product evidence. Verified new material evidence
continues through the existing evidence rules. A target with no grant remaining
stops visibly or the reviewer may select another eligible unvisited target;
it cannot bounce between already used targets.

The controller and user-facing status distinguish pending independent work from
an exhausted technical correction or a transport error. Routine approved handoffs
are delivered by the existing timer without an operator checkpoint. Existing
stalled historical results remain immutable: installation may re-review an exact
saved snapshot under the new typed contract in a separate protected job. It cannot
parse old nextAction prose as authority, overwrite its result, reset counters, or
open a new inference allowance. Only independently reviewed typed output activates
the bounded handoff and releases the matching operational gate.

## Review context and corrected-source resumption

A tool-less work review receives the exact hash-bound original verdict and its
reviewed objective as data. The proposed next target is separate; classifying the
past evidence as the proposed target is invalid. An exhausted diagnostic branch
cannot obtain another probe through a null work selection. A fresh valid
typed selection authorizes a new target or runtime checkpoint. The same-target
offline correction below uses the existing grant and typed independent rejection.

If a work review stalls because its installed source requires correction, a new
job is allowed only after the bound source files change, with the original
campaign, executor result and candidate intact. The complete previous job is
retained by a protected hash inventory. Its consumed review attempts are carried
forward before the new marker is exposed. A work re-review has a total ceiling of
three model calls across these jobs, independent of generic recovery windows.
Source changes, retries and new job names cannot renew that ceiling. An exhausted
review remains stopped; no old verdict is rewritten or promoted to authority.

## Same-target offline correction

An independent `changes_requested` review already requests correction of its
identified defects. Repeating the selected target in a nullable selection field
must not prevent that existing work from returning to its executor. The host may
derive exactly one same-target offline correction when the immediately active
protected grant is offline with one preparation and zero runtime checkpoints,
the reviewed pass equals that grant's next pass, and the validated review names
the same objective, has nonempty findings, offline scope, clean cleanup and no
owner request. Its source and evidence remain bound to the exact candidate.

The host never reads nextAction prose to choose this route. A null selection still
grants no new target or runtime. The derived checkpoint records
`workContinuationDerivation=same_target_offline_correction`, consumes preparation
slot two, and permits one executor launch. Further rejection cannot create a third
preparation or fall back to a technical route to evade that limit.

For an already stalled exact rejection, the host archives the stopped marker and
matching operational retry, replays the reviewed result without rewriting it or
adding objective history, persists the new checkpoint, and only then releases
that exact gate. Findings, preparation counters, inference ledgers and prior
review-call consumption remain unchanged. This recovery requires no new model
review and does not promote the rejected candidate to runtime or acceptance.

## Verification

Regressions must cross the real review/finish/checkpoint boundary: the previously
stalled approved handoff continues with typed authority, and unchanged counters,
authorization, history and ledger. Reject prose-only selection, same/unknown or
unapproved target, unresolved cleanup, missing/mismatched source/evidence, owner
requirement, repeated target, third preparation and second runtime. Exercise
interrupted launches, checkpoint replay, stale snapshots and exact current-stall
adoption. Failed checks never authorize runtime or entry into another target. A requested
offline correction of the active target consumes its remaining preparation slot;
it does not refund a grant. Real rollout verifies a new
executor pass; it does not claim that its product journey has passed.

## Fixed host execution of the reviewed Web ZIP journey

The owner-authorized assisted repair of the rejected pass237 packet is installed
as a fixed Web ZIP entrypoint. The existing campaign wrapper dispatches this
specific operation on the host, using a protected `webZipRequest` and the existing
`web-entries` runtime grant. It does not run a model to execute protected files,
introduce another service/counter, restore an offline allowance, or change the
inference ledger. `begin` and `finish` remain the existing controller operations.

The request binds the immutable predecessor as `previousReview`. The new
correction binds the request hash; the new review binds the correction; the
campaign selects that current review. This acyclic order preserves exact current
authority, candidate, pass, installed source hashes and desktop/product inputs.
The host validates the complete grant history before one launch. Source or request
changes require fresh review; an offline test verdict is not a runtime grant.

A host intent is published atomically and durably before invoking the installed
Node entrypoint. Interrupted intent, partial output and partial entrypoint intent
produce unresolved evidence without another guest launch. Reconciliation runs
before the normal phase gate, including when that gate has already moved a
consumed launch to review_pending. It neither restores active state nor decrements
counters. Protected host result and packet references bind the ordinary independent
review to exact output bytes. Only a completed, settled run supplies current-pass
runtime evidence; that evidence never changes documented acceptance by itself.

The owner separately authorized completing ordinary official Web login inside the
same owned Edge instance/profile. The fixed existing private LAB credential file
is read as data only, never sourced as shell code or copied into the request or
review package. SSH stdin carries runtime-only login material; DPAPI CurrentUser
protects its temporary Windows file. The official login form is submitted once,
with network recording disabled during authentication, inside the unchanged
600-second absolute operation budget. The parent verifies temporary login-file
removal independently of primary evidence writes. No copied cookies, registration,
password reset, OAuth reauthorization, credential rotation or new account is
permitted. A failed login is unresolved, not inferred owner action or acceptance.

Local Node/PowerShell process regressions use synthetic credentials and explicit
Windows/DPAPI/UI doubles. Their passing result does not establish native Windows,
PowerShell5.1, DPAPI transfer, an authenticated desktop, upload or scanner success.
Actual observed SID/session and the existing authorized product are required
before the protected runtime request can be admitted. The first-upload correction
below replaces the initial requirement for a pre-existing ZIP definition/revision. Original
review237, earlier packets, all preparation counts and the inference ledger remain
immutable. See `ops/joao/web-zip/README.md` and the host rollout procedure.

## Owner-authorized Web ZIP retry ceiling — 2026-11-17

Under AB#301 the owner explicitly authorized up to three Web ZIP attempts in total.
The consumed pass238 is attempt one, including its failed ASCII framing before SSH.
This amendment changes only the Web ZIP ceiling within `web-entries`; other targets
retain one runtime checkpoint. It does not reset the two offline preparation slots,
the historical runtime checkpoint, intents, results, review history or inference
ledger. Each additional checkpoint still permits one named executor pass and one
fresh protected request, with the same 600-second limit and no remediation model,
API key, new VM or account. The fourth attempt is rejected.

A second or third attempt requires a completed predecessor, an independent `pass`
with `bounded_no_model`, verified current cleanup, no owner request, changed actual
Web ZIP executable bytes and a recomputed different source fingerprint. The
existing `technicalCorrection` fields carry proof: `incident` is the exact prior
runtime checkpoint SHA; `regressionBefore` and `regressionAfter` name JSON receipts
in the new manifest. The correction binds that manifest; the review binds the
diagnosis and correction. A changed name, counter or error description is not proof.

Each closed receipt has `schema: 1`, `kind: web_zip_runtime_retry_regression`, the
failed `requestSha256`, tested `sourceFingerprint`, identical `command`, `outcome`
(`failed` before, `passed` after), integer `passed`, `failed`, `skipped`, identical
`regression` and `regressionSha256`, and `log: {name, sha256}`. The same regression
must fail before and pass after with equal test totals and zero skips. Regression
source and nonempty bounded logs are read through the existing checked artifact
reader and bound in the manifest. Before/after source fingerprints must match the
old/new executable inventories; one of the actual Web ZIP source hashes must change.

The complete protected history revalidates each extra checkpoint, its consumed
predecessor, exact current request and all proof hashes before dispatch. The new
request binds the prior checkpoint and the next pass; replay never creates another
intent or refunds an attempt. Old one-attempt records remain valid without adding
proof retroactively. Historical unresolved cleanup is preserved; a new verified
observation is a separate admission prerequisite, not a rewritten old result.

This amendment supports assisted repair and admission within the existing owner
authorization. It does not add autonomous source-repair scheduling after runtime
failure or create another offline correction grant. Failed runtime still requires
the concrete correction, regression, current cleanup and independent review before
the next available attempt can be admitted.


## Windows packet transport correction — 2026-11-17

Pass239 did not reach a verified Web upload. A separate inert 167161-byte script
reproduced the Windows PowerShell stdin stall. Bounded native probes also failed
both text-to-EOF and exact-byte-count reads of 131072 synthetic bytes; changing
only the reader is therefore not an accepted correction. These diagnostics do not
consume another Web ZIP journey or establish product acceptance.

Use the existing SSH/SFTP connection to stage only the nonsecret, hash-bound
worker and package. The staging directory is a separate request-bound sibling
under the already authorized laboratory runtime parent; it must not pre-create
the journey root, adopt an existing directory or follow reparse points. Establish
ownership before writing, verify the actual bytes before execution, and remove
only the owned staging resources under the original deadline. Failed or partial
transfer cannot authorize execution, verified cleanup or a repeated journey.

The official login remains runtime-only input to a short bootstrap, never SFTP
content, a command-line argument, diagnostic output or a plaintext guest file.
The bootstrap combines it with the verified public package in memory; the existing
worker still writes only its bounded DPAPI-protected temporary login artifact.
Prove the same bootstrap with synthetic credentials at the allowed maximum size,
including Unicode, before consuming the last authorized Web ZIP attempt.
Use the existing validated field limits with a compact UTF-8, newline-delimited
runtime frame (at most 4034 bytes); reject malformed encoding and extra fields.
JSON escaping must not enlarge this runtime input beyond the native reader's
proven bound. Reserve shell-wrapper space below the Windows command-line limit;
the encoded payload length alone does not measure the complete SSH invocation.

The parent and scheduled worker load only exact hash-verified source bytes through
ScriptBlock.Create. This avoids depending on execution of unsigned script files
under the observed Restricted policy without changing machine, user or process
execution policy. The existing 600-second total includes staging, invocation and
cleanup. No new service, VM, account, inference allowance, history reset, public
product endpoint or automatic repair budget is introduced. Offline and inert
transport evidence remain distinct from a successful Web ZIP journey.

The native setup also exposed inherited Authenticated Users Modify access on the
existing laboratory parent directories. Repair only their DACLs, preserving owners,
contents and the volume configuration. Path validation ignores InheritOnly ACEs
for the current object and distinguishes the exact C:\ volume: its observed
TrustedInstaller owner and effective CreateDirectories permission do not grant
mutation of the existing private laboratory directory. Every laboratory component
still rejects foreign effective mutation rights, including deletion, ACL/owner
changes and generic write/all. The volume exception cannot apply below that root.

## Owned browser profile disposal after pass240 — 2026-11-17

Pass240 consumed the third Web ZIP attempt and remained inconclusive. Transport
settled, but the parent rejected the scheduled task's account-name representation
of the authorized SID. A later read-only observation also found an explicit
capability-SID Modify ACE on the owned temporary profile's `Default/Cache`
directory. Strict tree removal would reject that directory even after the task
principal correction. This is a separate cleanup defect; it does not establish
the cause of the browser journey failure or change its historical result.

Keep the execution-time path validator strict. Do not allowlist capability SIDs
or foreign write access generally. After the owned browser job and processes are
verified quiescent, a disposal-only operation may restrict the DACL of the exact
request-bound temporary profile and its descendants before the existing strict
tree removal. It may not touch another profile, the runtime parent, product data,
the machine's execution policy, or any credential contents.

The operation binds the profile's canonical location, owner and creation identity
to the owned runtime. Open each object with `OPEN_EXISTING`,
`FILE_FLAG_OPEN_REPARSE_POINT` and `FILE_FLAG_BACKUP_SEMANTICS`, retaining its
handle without sharing write or delete access. Validate the handle's final path,
volume/file identity, creation time, owner and attributes before mutation. Reject
reparse points, unexpected owners, changed identities and files with more than
one hard link: changing a hard-linked file's DACL would affect names outside the
profile. Reject foreign effective WRITE_DAC, WRITE_OWNER or GENERIC_ALL rights;
share modes alone do not exclude handles with security-management rights.

Use `SetSecurityInfo` on the verified handle, changing only a non-null protected
DACL granting FullControl to the authorized desktop SID, SYSTEM and built-in
Administrators. Preserve the owner. Open with `MAXIMUM_ALLOWED` so this operation
does not propagate ACEs to uninspected children; the replacement ACEs also have no
inheritance or propagation flags. Restrict and verify each directory before
enumerating its children, and keep the handle until that object's restriction is
verified. Denied sharing or any changed generation fails closed. This is removal
of foreign access for disposal, not approval of the previous ACL for execution.

Bound traversal by the existing cleanup deadline and an explicit entry limit.
Read only identity, attributes and security metadata; do not inspect cookies or
other profile contents. Revalidate restricted objects with the existing strict
path validator before deletion. Any partial restriction, failed verification or
remaining object yields unresolved cleanup with its own evidence; do not restore
foreign permissions, broaden access, skip the object or report success. Protected
history and original runtime receipts remain unchanged.

Regression must cover the observed explicit capability Modify ACE, foreign
security-management rights, reparse points, hard links, unexpected owners,
generation changes, open writers and partial failure. Local doubles do not prove
Windows handle/share/ACL behavior: use bounded native inert fixtures when that
boundary requires verification, without a browser, login, product action or new
Web ZIP journey. Microsoft documents the relevant boundaries in
[CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)
and [SetSecurityInfo](https://learn.microsoft.com/en-us/windows/win32/api/aclapi/nf-aclapi-setsecurityinfo).

This correction and exact residue settlement remain within the authorized
laboratory repair. They grant no fourth Web ZIP attempt, replay, quota reset,
inference call or new VM. Another journey requires a separate owner decision.
